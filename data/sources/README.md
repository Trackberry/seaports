# Build inputs

Files here feed `rake seaports:refresh` and are not shipped in the gem; only the table they help build is.

## subdivision_overrides.csv

Reviewed ISO 3166-2 subdivisions for ports that neither UN/LOCODE nor Natural Earth's map places, such as Valencia, Algeciras and Barcelona, which have no subdivision and no position in UN/LOCODE. An override wins over every other source, so a row should be removed once UN/LOCODE publishes a subdivision of its own; each refresh lists the rows that have reached that point.

The rows were suggested by `script/suggest_subdivision_overrides.rb` and checked by a person. The `note` column quotes the place each search matched, or explains a manual correction.

Those place names come from [OpenStreetMap](https://www.openstreetmap.org/copyright) through its Nominatim search: © OpenStreetMap contributors, available under the Open Database Licence (ODbL).

## coordinate_overrides.csv

Reviewed positions for ports UN/LOCODE publishes no coordinates for: the port area (harbour or terminals), not the city centre, to four decimals. Columns: `locode`, `name` (for review, ignored by the build), `lat`, `lng`, `source` (required) and `note`, which opens with `high` or `medium` for how sure the placement is, then names the place.

Unlike a subdivision override, a coordinate override never replaces a UN/LOCODE position, because UN/LOCODE is the source of record. It fills a gap only; once UN/LOCODE publishes a position of its own, the refresh reports the row so it can be removed. It also reports a row whose port left UN/LOCODE.

The seed rows were placed by hand from general knowledge of each port, to roughly a kilometre, then each was checked by reverse geocoding it on [OpenStreetMap](https://www.openstreetmap.org/copyright) (© OpenStreetMap contributors, ODbL; one request a second, per Nominatim's usage policy): the point must land in the port's own town, on or by its harbour. Three did not and were moved; their `note` says where they were first placed. Do the same check before adding a row, and tighten the `medium` ones against the harbour and terminal outlines when a berth matters. The build rejects a row with no source, a position off the globe, a malformed locode or a port listed twice.

After adding rows, run `rake seaports:apply_coordinates` to write them into the shipped table without a download. The next refresh rebuilds the same positions on its own.

## coordinates_wpi.csv and wpi/

Generated by `rake seaports:refresh_wpi`; do not edit by hand. Positions from the [NGA World Port Index](https://msi.nga.mil/Publications/WPI) (Pub. 150), which NGA publishes as `UpdatedPub150.csv`: a work of the US government, in the public domain, credited here as NGA asks. Columns as in `coordinate_overrides.csv` without the note; the `source` names the snapshot.

`wpi/UpdatedPub150.csv` is the vendored copy the file is generated from, with the byte order mark and Windows line endings removed, and `wpi/provenance.json` records where it came from (NGA, or the Internet Archive's snapshot of NGA's URL while NGA is in maintenance), the snapshot date, when it was retrieved and its sha256. A row is written only for a port in the table that UN/LOCODE and `coordinate_overrides.csv` give no position, whose WPI position is on a valid UN/LOCODE shared by no other WPI port and within 50 km of its country.

## alternate_names.csv and alternate_names_wpi.csv

Other names for ports, merged by `Seaports::AlternateNames` into the table's `alternate_names` column: this reviewed file first, then the World Port Index file, then the English name in the parentheses of UN/LOCODE's own name.

`alternate_names.csv` is typed by a person. Columns: `locode`, `name`, `source` (required: what makes it a name for that port). One row per name. The build rejects a malformed locode, a blank name or source, and the same name twice for a port. Before adding a row, check the port in the table and that the World Port Index does not already list the name in its "Alternate Port Name" column, then run `rake seaports:apply_alternate_names` to write it into the table without a download.

`alternate_names_wpi.csv` is generated by `rake seaports:refresh_wpi` from the vendored index, with the coordinates; do not edit it. Its "Alternate Port Name" column is split on `;`. A row is written only for a locode in the table that is on exactly one index row. The index's own spelling of a port's name is kept in the file when it differs from the table's; the build drops any name that equals the table's name once case, accents and punctuation are ignored.

`alternate_names_rejected.csv` is reviewed by a person too: `locode`, `name`, `reason` (required). A name listed for a port is dropped from it whichever source offers it, ignoring case, accents and punctuation. It holds the wrong-place names that got past the index filter (a city, a state, an island, a country). The build also drops, with no row needed, a name that is another port's own name in the same country and a name that two or more ports of a country share. The index file is generated with these filters: split on `;` and `,`; no name starting with FSO, FPSO, FSPO or MV, or holding the words Terminal, Term, Base, Oil, Naval, Sadamate or Petroleum, or ending in AS; no country name; nothing under four characters. A refresh that loses more than 5% of the names already in `alternate_names_wpi.csv` is refused.

## coordinates_wikidata.csv

Generated by `rake seaports:refresh_wikidata`; do not edit by hand. Positions from [Wikidata](https://www.wikidata.org) (CC0): items with a UN/LOCODE (P1937) and coordinates (P625). The `source` column names the item. Written only for ports nothing above it places, and only from items typed as a port or harbour (a town item is a city centre, often inland, so a code with none is left out). Where a code is on several port items they must lie within 10 km of each other, and if it is also on a town item the port item must be within 50 km of it, or the code is skipped. `wikidata_provenance.json` records when the file last changed and how many codes the query returned; it is written only with a change, so an unchanged file does not make a weekly pull request.

The table's `coordinate_source` column records which of these (or UN/LOCODE) each position came from.

Precedence, highest first: UN/LOCODE, `coordinate_overrides.csv`, the World Port Index, Wikidata.
